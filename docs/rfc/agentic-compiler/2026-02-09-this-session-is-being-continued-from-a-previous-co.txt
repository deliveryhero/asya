  ★ Insight ─────────────────────────────────────

  What I learned from studying ADK internals (real source code, not docs):

  1. ADK's orchestration agents are surprisingly simple —
  SequentialAgent._run_async_impl is just a for loop over sub-agents, yielding
  their events. LoopAgent wraps that in another loop with max_iterations.
  ParallelAgent uses asyncio.TaskGroup. The complexity lives in BaseLlmFlow,
  which handles the ReAct loop (call LLM → detect tool calls → execute → feed
  back → repeat).
  2. All ADK orchestration works by generator composition — a parent agent
  yields events from child agents via async for event in
  sub_agent.run_async(ctx): yield event. This is in-process generator nesting —
  which fundamentally cannot work in a distributed system where each agent runs
  on a different pod.
  3. ADK's tool execution is in-process too — when BaseLlmFlow detects a tool
  call, it executes the tool function locally and feeds the result back. No
  message passing, no queues.

  ─────────────────────────────────────────────────

  What ADK does internally at SequentialAgent level

  From the actual sequential_agent.py source I fetched:

  async def _run_async_impl(self, ctx: InvocationContext) ->
  AsyncGenerator[Event, None]:
      for i in range(start_index, len(self.sub_agents)):
          sub_agent = self.sub_agents[i]
          async with Aclosing(sub_agent.run_async(ctx)) as agen:
              async for event in agen:
                  yield event
                  if ctx.should_pause_invocation(event):
                      return

  This is generator composition — the parent yields child events. Each
  sub_agent.run_async(ctx) returns an async generator. The parent iterates it,
  forwarding events.

  The Key Transformation: CPS (Continuation-Passing Style)

  The user's vision is to take an async function and treat each await as a split
   point. This is essentially CPS transformation applied to message passing:

                        async function                          actor network
                        ──────────────                          ─────────────
                   ┌─ code before await ─┐              ┌─ Actor A (router) ─┐
                   │                     │              │ prepares payload,   │
                   │ state = await X()   │  ──compile──▶│ sends to X         │
                   │                     │              └────────────────────┘
                   │ code after await    │              ┌─ Actor X           ─┐
                   │ state = await Y()   │              │ does work, returns  │
                   │                     │              └────────────────────┘
                   │ return state        │              ┌─ Continuation Rtr  ─┐
                   └─────────────────────┘              │ receives X result,  │
                                                        │ sends to Y          │
                                                        └────────────────────┘

  Each await splits the function into:
  - Before-await → current actor (does work, sends message)
  - After-await → continuation actor (receives result, continues)

  Applying to the LLM Auditor

  Step 1: User writes the Asya async flow (simplified version of ADK's
  SequentialAgent):

  # asya flow (async version)
  async def llm_auditor(state: dict) -> dict:
      state = await critic(state)     # await split #1
      state = await reviser(state)    # await split #2
      return state

  Step 2: But critic is an LLM agent with tools. The user writes its event loop
  too:

  async def critic(state: dict) -> AsyncGenerator[dict, None]:
      messages = state.get("messages", [{"role": "user", "content":
  state["query"]}])

      while True:
          response = await llm_call(messages, model="gemini-2.5-flash")  # await
   split

          if response.tool_calls:
              for tc in response.tool_calls:
                  result = await google_search(**tc.args)  # await split
                  messages.append({"role": "tool", "content": result,
  "tool_call_id": tc.id})
          else:
              # Last yield = control event (our Option B convention)
              yield {"type": "result", "critique": response.text, "messages":
  messages}
              return

  Step 3: Compiler decomposes at each await

  The compiler sees:
  1. await llm_call(...) → split: send to LLM actor, finish
  2. await google_search(...) → split: send to tool actor, finish
  3. while True → loop: generate a router that loops back
  4. if response.tool_calls → conditional: generate a dispatch router
  5. yield {"type": "result", ...} → final event: pass to next actor in parent
  flow

  The Compiler's Job: Decomposing at await

  Here's what the compiler does, step by step:

  # INPUT: User's async function
  async def critic(state: dict) -> AsyncGenerator[dict, None]:
      messages = state.get("messages", [])          # ← mutation (batched into
  router)

      while True:                                    # ← loop construct
          response = await llm_call(messages)        # ← SPLIT: actor "llm-call"

          if response.tool_calls:                    # ← conditional (router)
              for tc in response.tool_calls:
                  result = await google_search(tc)    # ← SPLIT: actor
  "google-search"
                  messages.append(tool_result(tc, result))  # ← mutation
  (collect-router)
          else:
              yield {"type": "result", ...}          # ← control event → next
  actor
              return

  Compiler output — pseudo-IR:
  BLOCK entry:
      mutation: messages = state.get("messages", [])
      goto: llm_call

  BLOCK llm_call:
      actor: llm_call(messages) → response
      goto: dispatch

  BLOCK dispatch:
      if response.tool_calls:
          goto: google_search
      else:
          emit_result(state)
          goto: NEXT_IN_PARENT  # returns to parent flow

  BLOCK google_search:
      actor: google_search(tc.args) → result
      goto: collect

  BLOCK collect:
      mutation: messages.append(tool_result(tc, result))
      goto: llm_call  # loop back

  Each BLOCK becomes either an actor (if it has actor:) or a generated router
  (if it only has mutations/conditionals/gotos).

  What About Streaming?

  During step 2 and 8 (LLM calls), the actors can yield partial text deltas via
  the streaming side-channel:

  async def llm_call(state: dict) -> AsyncGenerator[dict, None]:
      messages = state["messages"]

      async for chunk in gemini.generate_content_async(messages, stream=True):
          if chunk.text:
              yield {"type": "text_delta", "delta": chunk.text}  # → HTTP →
  gateway → user
          if chunk.tool_calls:
              yield {"type": "result", "tool_calls": chunk.tool_calls}  # →
  queue → dispatch-router
              return

      yield {"type": "result", "text": full_response}  # → queue → next actor

  The sidecar classifies events:
  - type: "text_delta" → HTTP side-channel → gateway → SSE to user
  - type: "result" → queue → next actor (the last yield, per our Option B
  convention)

  The Two Compilation Levels

  What emerges from this analysis is that there are two distinct levels the
  compiler handles:

  Level 1: Orchestration compilation (SequentialAgent → flow)
  # ADK declarative:
  SequentialAgent(sub_agents=[critic, reviser])

  # Asya async function:
  async def llm_auditor(state):
      state = await critic(state)
      state = await reviser(state)
      return state

  # Compiled: linear route [critic, reviser]
  This is what the current flow compiler already does (sequential, conditional,
  fan-out).

  Level 2: Agent decomposition (LlmAgent with tools → ReAct loop actors)
  # ADK declarative:
  Agent(model="gemini", tools=[google_search])

  # Asya async function:
  async def critic(state) -> AsyncGenerator:
      while True:
          response = await llm_call(state)     # split
          if response.tool_calls:
              result = await tool(state)        # split
          else:
              yield result                      # done
              return

  # Compiled: llm-call → dispatch-router → [tools] → collect-router → (loop)
  This is new — the flow compiler doesn't handle while loops, await split
  points, or async generators today.

  What the Compiler Needs to Learn

  To support Level 2, the flow compiler needs three new capabilities:

  1. await as split point: Each await expr becomes a message send + actor
  boundary
  2. while True as loop: The compiler generates a router that loops back to a
  previous actor
  3. AsyncGenerator yield convention: Intermediate yields → streaming
  side-channel, last yield → control event → queue

  These map directly to what ADK's internal orchestration does — but transformed
   from in-process generator nesting to distributed message passing.

  ★ Insight ─────────────────────────────────────

  The core transformation is CPS (Continuation-Passing Style): Each await in the
   user's code becomes a continuation boundary. The compiler transforms:
  x = await A()
  y = await B(x)
  Into:
  Actor-1: call A, put result in payload, route to Actor-2
  Actor-2: read A's result from payload, call B, route to next

  This is exactly what Go does with goroutines at the runtime level (stack
  splitting at function calls), and what JavaScript does with async/await
  transpilation to .then() chains. The Asya compiler does the same thing, but
  across network boundaries.
