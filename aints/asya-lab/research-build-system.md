# Research: Handler-to-Image Mapping and Build System Integration

**Date**: 2026-03-19
**Status**: In progress (needs experimentation)
**Context**: How the compiler resolves handler functions to container images.
Emerged from brainstorming session on compiler simplification (see
`compiler-simplify/rfc.md`).

---

## 1. The Two Problems

### 1.1 Handler Identity (solved)

Given a handler function name in a flow, resolve it to the actual Python
function and source file. This is solvable via Python's `inspect` module
(importing the module and using `inspect.getfile()`). The compiler uses
the project's Python interpreter (auto-detected from venv/uv/poetry or
`--python` override).

**Decision**: trust the local Python environment for handler identity.

### 1.2 Image Binding (open)

Given a resolved handler function, determine which container image it
lives in and what its in-container module path is. This is the hard
problem because:

- Python's import system knows modules, not images
- The mapping is a deployment concern, external to Python
- The local dev module path may differ from the in-container path
- Images may not exist yet when the compiler runs
- One handler package could be in multiple images (N:M relationship)

**Current implementation**: fragile string-prefix matching in
`project.py:resolve_image()` against `build:` entries in config.yaml.
`handler_name.startswith(module.replace(".", "_"))` -- opaque and
hard to debug.

## 2. Approaches Explored

### 2.1 Central config (RFC's `images.default + overrides`)

```yaml
images:
  default: ghcr.io/team/actors:latest
  overrides:
    nlp_actors.handler: ghcr.io/team/nlp:latest
```

- **Rejected**: scales O(n) per handler, causes merge conflicts in
  monorepos, separated from the code it describes.

### 2.2 Per-handler registry (`.asya/registry.yaml`)

Generated by `asya analyze`, maps each handler FQN to image + module path.

- **Rejected**: O(n) entries per handler, stale registry problem.

### 2.3 Colocated `.asya/` directories (walk-up inheritance)

Place `.asya/config.yaml` in each actor directory with image config.
Uses existing walk-up merge.

- **Rejected**: pollutes repo with many `.asya/` directories.

### 2.4 BUILD files (Pants/Bazel pattern)

Small colocated files next to actor code with Pants-style `__defaults__`
hierarchical inheritance.

- **Rejected**: inventing a new file format. Pants/Bazel themselves are
  too heavy as dependencies.

### 2.5 Module-prefix map

Flat dict of module prefixes to images with longest-prefix match.

- **Partially viable**: simple concept, but still a central config that
  doesn't self-describe the project structure.

## 3. Promising Direction: Build Tools as Source of Truth

### 3.1 Core Insight

The handler-to-image mapping is fundamentally a build system concern.
Build tools already answer "which source directories produce which
images." Instead of reinventing this mapping, asya should read it from
the project's build configuration.

### 3.2 Cloud Native Buildpacks (CNB)

Buildpacks are the most self-consistent model: **source directory IS
the build unit**. No Dockerfile needed. Presence of a dependency file
(`requirements.txt`, `pyproject.toml`, `uv.lock`) self-describes the
build unit.

**`project.toml`** -- CNB standard project descriptor. Already supports:
- Project name (`[_].name`)
- Builder selection (`[io.buildpacks].builder`)
- File include/exclude (gitignore syntax)
- Build environment variables
- Free-form metadata (`[_.metadata]`) -- asya can use this

**Strengths**: zero-config for simple Python, standard format, no
Dockerfile needed for DS.

**Weaknesses**: GPU/CUDA 2/5 (requires custom run image), limited
system package support, no `uv` support in Paketo yet.

### 3.3 Three-Tier Build Model

| Actor type | Build marker | Strategy | DS effort |
|---|---|---|---|
| Simple Python | `project.toml` / `requirements.txt` | Buildpacks | Zero config |
| GPU/CUDA | `Dockerfile` | Docker build | Write Dockerfile |
| Pre-built / external | No local build | Config only | Declare image |

Discovery rule: scan for directories containing build markers.
`Dockerfile` takes precedence over `project.toml` when both present.

**Open**: pre-built images should NOT go in a separate `.asya/config.yaml`
(separated configuration is bad design). Need a unified model.

### 3.4 Skaffold / Tilt as Build Orchestrators

Build tools like Skaffold aggregate the build context -> image mapping
in a single file:

```yaml
# skaffold.yaml
build:
  artifacts:
    - image: ghcr.io/team/nlp
      context: actors/nlp/
      buildpacks:
        builder: paketobuildpacks/builder:base
    - image: ghcr.io/team/gpu-model
      context: actors/gpu-model/
      docker:
        dockerfile: Dockerfile
```

**What they solve**: which directories are built, which builder to use,
mixed strategies (buildpacks + Dockerfile) in one config.

**What they do NOT solve**:
1. Image repo + tag -- skaffold.yaml has the image *name* but tagging
   strategy is separate (git SHA, datetime, custom)
2. In-container Python module paths -- which Python modules are
   available inside the image and under what import name
3. Pre-built images -- only covers things that are built, not
   pre-existing images from external sources

**Trade-off with Skaffold**:

| Aspect | With Skaffold | Without |
|---|---|---|
| New dependency | Yes (CLI tool) | No |
| Config format | Standard | Custom |
| Build execution | Mature, battle-tested | Shell out to pack/docker |
| File watching | Built-in | Must implement |
| Learning curve | Skaffold concepts | Asya-only |
| Image naming | Partially solved | Must design |

**Trade-off with Tilt**:

Tilt uses a programmable `Tiltfile` (Starlark). More flexible than
YAML but less standard. Better for local dev (live reload). Docker
Inc maintains it. Needs hands-on evaluation.

## 4. Remaining Open Questions

### Q1: In-container module path

When the compiler resolves `from nlp_actors.handler import classify`,
it knows the local module path. But in the container image, the module
might be at a different path (depending on how source was COPY'd or
pip-installed). How does asya determine the in-container import path?

With buildpacks: source is always at `/workspace/`. Predictable.
With Dockerfile: depends on COPY directives. Must parse or configure.

### Q2: Image repo + tag

Where does the full image reference come from? Skaffold has the image
name but tagging is separate. Options:
- Convention: `{registry}/{project.toml name}:{git-sha}`
- Explicit in skaffold.yaml + tagging policy
- `project.toml` metadata extension

### Q3: Pre-built / external images

Handlers from pip-installed packages or external team images have no
build context. The mapping must come from somewhere. A separate config
file is bad (split configuration). Options:
- Extend skaffold.yaml/Tiltfile with non-build artifacts
- `project.toml` metadata for the consuming flow
- Flow-level config (per-flow image overrides)

### Q4: N:M relationship

One handler package in multiple images (e.g., CPU and GPU variants).
Disambiguation needed. Options:
- Flow-level override ("in this flow, use the GPU image for X")
- Most-specific-prefix wins
- Error on ambiguity

### Q5: Asya's role in the build

Is asya a thin wrapper that delegates to Skaffold/Tilt, or does it
have its own build execution? The RFC says "asya is a thin command
runner for builds, not a build system." This aligns with delegating
to Skaffold/Tilt.

### Q6: Dockerfile COPY parsing reliability

For Dockerfile-based actors, can asya reliably parse COPY directives
to determine which modules are baked in? Works for simple cases
(`COPY ./src /app`), fails for variable expansion (`COPY ${DIR} /app`),
multi-stage (`COPY --from=builder`). Is best-effort parsing acceptable,
or must Dockerfile actors always have explicit config?

## 5. Next Steps

1. **Experiment with Skaffold** -- set up a sample multi-actor project
   with mixed buildpacks + Dockerfile builds. Evaluate DX.
2. **Experiment with Tilt** -- same project, compare DX with Skaffold.
3. **Prototype `asya analyze`** -- implement directory scanning that
   detects build units and suggests the handler-to-image mapping.
4. **Design unified config model** -- where pre-built image config
   lives without being separated from the rest.
5. **Test in-container module path resolution** -- verify that buildpack
   images have predictable PYTHONPATH (`/workspace/`).

---

## 6. Design Principles (from brainstorming)

1. Handler functions stay clean -- no image info in decorators
2. `@actor` decorator is the discovery marker
3. Build tool (Skaffold/Tilt/native) is the source of truth for
   "which dirs produce which images"
4. Asya auto-discovers the setup and is as explicit as possible
5. Scaling to many images should be constant effort
6. No package requirement -- asya works with any Python file
7. No new file formats if avoidable -- use existing standards
   (project.toml, skaffold.yaml, Dockerfile)
