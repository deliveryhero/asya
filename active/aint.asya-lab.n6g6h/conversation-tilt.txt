  ---
  Three Approaches for Tilt-based Dev Loop

  Approach A: asya dev generates and runs Tilt (Max Integration)

  How it works: asya dev my-actor reads .asya/config.yaml, generates a temporary Tiltfile, applies a dev kustomize overlay (pins
  replicas=1, disables KEDA), and runs tilt up.

  $ asya dev my-actor --context stg
  [+] Generated dev overlay (replicas: 1, KEDA disabled)
  [+] Generated Tiltfile from .asya/config.yaml
  [+] Starting tilt up...
       Tilt dashboard: http://localhost:10350
       Watching: ./handler.py, ./utils.py

  The generated Tiltfile would look like:
  # Auto-generated by asya dev — do not edit
  custom_build(
      'registry/my-actor',
      command='echo $EXPECTED_REF',  # no-op, uses existing image
      deps=['./src/handler.py'],
      skips_local_docker=True,
      live_update=[
          sync('./src/handler.py', '/app/handler.py'),
          restart_container(),
      ]
  )
  k8s_yaml(kustomize('.asya/manifests/my-actor/overlays/dev'))

  Upgrade path for auto-recompile flows:
  local_resource(
      'compile-order-flow',
      cmd='asya flow compile flows/order_processing.py',
      deps=['flows/order_processing.py'],
  )

  Pros: One command, zero Tilt knowledge, config-driven, auto dev overlay.
  Cons: Tilt becomes a required dependency, generated Tiltfile is opaque, hard to customize.

  ---
  Approach B: Tiltfile template + Asya helpers (Balanced) -- Recommended

  How it works: asya init generates a Tiltfile in the project root as a first-class artifact. The Tiltfile imports a small Python
  helper from asya_lab that reads config and provides convenience functions. User owns the Tiltfile and can customize.

  # Tiltfile (generated by asya init, user-owned)
  load('ext://asya', 'asya_actor', 'asya_flow')

  # Dev a single actor — syncs handler code, pins replicas=1
  asya_actor(
      'my-actor',
      sync_paths=['./src/handler.py', './src/utils.py'],
      install_deps=False,   # True = run pip install on requirements.txt change
  )

  # Optional: auto-recompile a flow on change
  asya_flow(
      'order-processing',
      flow_file='./flows/order_processing.py',
  )

  Under the hood, asya_actor() would:
  1. Read .asya/config.yaml for image, handler path, namespace, context
  2. Generate custom_build() with live_update (sync + restart)
  3. Apply a dev overlay that patches the ScaledObject/Deployment (replicas=1)
  4. Set up k8s_resource with log streaming

  The asya_flow() helper would:
  1. Watch the flow .py file
  2. On change, run asya flow compile
  3. Apply updated manifests (router ConfigMaps, new/removed actors)

  Pros: User owns and can customize the Tiltfile. Standard Tilt patterns (extensions). Config-driven but transparent. Tilt
  community would recognize the pattern.
  Cons: User needs basic Tilt understanding. Tilt extension needs to be published/distributed.

  ---
  Approach C: Native asya dev --watch (No Tilt)

  How it works: Skip Tilt entirely. asya dev my-actor --watch uses watchfiles (Python) to watch handler files, syncs via kubectl
  cp, and restarts the container via kubectl exec.

  $ asya dev my-actor --watch --context stg
  [+] Pinned my-actor replicas to 1
  [+] Watching: ./src/handler.py, ./src/utils.py
  [+] Synced handler.py -> my-actor-pod:/app/handler.py (0.3s)
  [+] Restarted asya-runtime container (1.2s)
       ...editing handler.py...
  [+] Change detected: handler.py
  [+] Synced handler.py -> my-actor-pod:/app/handler.py (0.3s)
  [+] Restarted asya-runtime container (1.2s)

  Pros: Zero external dependencies, fully integrated, simplest mental model.
  Cons: Reinvents Tilt (file watching, sync, restart, error handling, dashboard). No Tilt dashboard UI. Less mature. Doesn't scale

  ---
  Deep Technical Analysis: Tilt + Asya

  1. Can Tilt work without a Dockerfile?

  Yes, through three mechanisms:

  ┌────────────────────────────────────────┬───────────────┬────────────────────┬──────────────┐
  │               Mechanism                │ Needs Docker? │ Needs Image Build? │ Live Update? │
  ├────────────────────────────────────────┼───────────────┼────────────────────┼──────────────┤
  │ docker_build + dockerfile_contents     │ Yes (local)   │ Yes (thin layer)   │ Yes          │
  ├────────────────────────────────────────┼───────────────┼────────────────────┼──────────────┤
  │ custom_build + skips_local_docker      │ No            │ Yes (any builder)  │ Yes          │
  ├────────────────────────────────────────┼───────────────┼────────────────────┼──────────────┤
  │ k8s_custom_deploy + container_selector │ No            │ No                 │ Yes          │
  └────────────────────────────────────────┴───────────────┴────────────────────┴──────────────┘

  k8s_custom_deploy is the key discovery for Asya's "no build" scenario:

  k8s_custom_deploy(
      'my-actor',
      apply_cmd='kubectl apply -f asyncactor-dev.yaml',
      delete_cmd='kubectl delete -f asyncactor-dev.yaml',
      deps=['asyncactor-dev.yaml'],
      container_selector='asya-runtime',   # targets by container NAME
      live_update=[
          sync('./src/handler.py', '/app/handler.py'),
          run('date > /tmp/.reload'),      # trigger reload (see section 3)
      ]
  )

  No image build at all. Tilt applies the CRD, finds the pod with a container named asya-runtime, and syncs files directly into
  it. The image can come from CI, be a plain python:3.13-slim, or be built by any tool — Tilt doesn't care.

  2. How does Tilt know where files are mounted?

  It doesn't. You tell it.

  sync('./src/handler.py', '/app/handler.py')
  #    ^^^^ local path       ^^^^ container path (you specify)

  The user (or our generated Tiltfile) explicitly maps local paths to container paths. No auto-detection, no Dockerfile parsing.

  For Asya, we can derive the container path from config:
  - ASYA_HANDLER=handler.process → module handler → file handler.py
  - PYTHONPATH=/app (convention or from image)
  - Therefore: sync ./handler.py → /app/handler.py

  This mapping is something asya init can generate into the Tiltfile based on .asya/config.yaml.

  3. The K8s Restart Problem (Critical Finding)

  This is the biggest technical constraint I found. There are three restart mechanisms in Tilt, and only one works for our case:

  ┌──────────────────────────┬──────────────────────────┬──────────────────────────┬──────────────────┐
  │        Mechanism         │      Works in K8s?       │ Works with custom_build? │ Works with CRDs? │
  ├──────────────────────────┼──────────────────────────┼──────────────────────────┼──────────────────┤
  │ restart_container()      │ No (Docker Compose only) │ N/A                      │ N/A              │
  ├──────────────────────────┼──────────────────────────┼──────────────────────────┼──────────────────┤
  │ restart_process ext      │ Yes                      │ No                       │ No               │
  ├──────────────────────────┼──────────────────────────┼──────────────────────────┼──────────────────┤
  │ Application-level reload │ Yes                      │ Yes                      │ Yes              │
  └──────────────────────────┴──────────────────────────┴──────────────────────────┴──────────────────┘

  Why restart_container() is out: It's explicitly Docker Compose only per the docs.

  Why restart_process is out: The extension wraps the container entrypoint with a Go binary (tilt-restart-wrapper). The docs
  explicitly state it does not work with custom_build, CRDs, or distroless images. And it would conflict with Asya's injector
  which overrides the container command.

  Why kill 1 is out: In K8s, when a container exits and the kubelet restarts it, the writable layer is reset — a new container is
  created from the image. Any files Tilt synced are gone. This is fundamental to K8s design (unlike docker restart which preserves
   the layer).

  The solution: hot-reload in asya_runtime.py.

  The runtime already loads the handler via importlib.import_module(). Adding file-change detection + module reimport is
  straightforward:

  # In asya_runtime.py — dev mode addition
  import os, importlib

  def _watch_handler(handler_module, handler_path):
      """Poll handler file, reimport on change."""
      last_mtime = os.path.getmtime(handler_path)
      while True:
          time.sleep(0.5)
          mtime = os.path.getmtime(handler_path)
          if mtime != last_mtime:
              last_mtime = mtime
              importlib.reload(handler_module)
              log.info(f"[+] Handler reloaded: {handler_path}")

  With hot-reload:
  1. Tilt syncs handler.py → /app/handler.py (container writable layer)
  2. Runtime detects mtime change → importlib.reload() → new handler active
  3. Container never restarts → writable layer never reset → synced files persist
  4. Sub-second reload (<100ms), no downtime

  This is the same pattern Flask uses with debug=True — and it's what the Tilt docs recommend when restart_process isn't
  available.

  Activation: ASYA_DEV_RELOAD=true env var. Default off — no impact on production behavior.

  4. Pip deps synchronization

  Two modes, user chooses via Tiltfile:

  Mode A: Deps pre-baked in image (CI-built)
  k8s_custom_deploy(
      'my-actor',
      apply_cmd='kubectl apply -f asyncactor.yaml',
      delete_cmd='kubectl delete -f asyncactor.yaml',
      container_selector='asya-runtime',
      live_update=[
          fall_back_on(['requirements.txt']),  # dep change → full redeploy
          sync('./src/', '/app/'),             # code change → fast sync
      ]
  )
  When requirements.txt changes, fall_back_on triggers a full redeploy (user rebuilds image via CI, updates CRD).

  Mode B: Plain base image (pip install in container)
  k8s_custom_deploy(
      'my-actor',
      apply_cmd='kubectl apply -f asyncactor.yaml',
      delete_cmd='kubectl delete -f asyncactor.yaml',
      container_selector='asya-runtime',
      live_update=[
          sync('./requirements.txt', '/app/requirements.txt'),
          sync('./src/', '/app/'),
          run('pip install -r /app/requirements.txt',
              trigger=['./requirements.txt']),   # only on dep change
      ]
  )
  Pip runs inside the container. Ephemeral (lost on pod restart), but fine for dev — Tilt re-syncs and re-installs. First sync is
  slower (~30s for pip), subsequent code-only syncs are instant.

  No Dockerfile needed for either mode. Tilt's run() executes arbitrary commands inside the container.

  5. Build system compatibility

  live_update is completely build-system-agnostic. The sync step uses the K8s API (kubectl exec-style), not Docker. It works with
  any image regardless of how it was built.

  For the initial image build (when you DO need to rebuild):

  ┌────────────┬───────────────────────────────────────────────────────────────────────────────┬───────────────────────────────┐
  │  Builder   │                                Tilt mechanism                                 │            Example            │
  ├────────────┼───────────────────────────────────────────────────────────────────────────────┼───────────────────────────────┤
  │ Dockerfile │ docker_build() or custom_build('docker build ...')                            │ Standard                      │
  ├────────────┼───────────────────────────────────────────────────────────────────────────────┼───────────────────────────────┤
  │ Buildpacks │ custom_build('pack build $EXPECTED_REF --publish', skips_local_docker=True)   │ No Docker needed              │
  ├────────────┼───────────────────────────────────────────────────────────────────────────────┼───────────────────────────────┤
  │ apko       │ custom_build('apko publish apko.yaml $EXPECTED_REF', skips_local_docker=True) │ No Docker needed              │
  ├────────────┼───────────────────────────────────────────────────────────────────────────────┼───────────────────────────────┤
  │ Cog        │ custom_build('cog build -t $EXPECTED_REF', ...)                               │ Needs Docker (Cog limitation) │
  ├────────────┼───────────────────────────────────────────────────────────────────────────────┼───────────────────────────────┤
  │ No build   │ k8s_custom_deploy(apply_cmd='kubectl apply ...')                              │ Image already exists          │
  └────────────┴───────────────────────────────────────────────────────────────────────────────┴───────────────────────────────┘

  The key insight: live_update doesn't care about the builder. Whether the base image came from buildpacks, apko, or Docker — Tilt
   just syncs files into whatever container is running.

  apko is particularly interesting: since apko can't COPY files, the handler was never in the image to begin with. Tilt fills
  exactly that gap — syncing handler code into a deps-only base image.

  7. Crossplane interaction

  One subtlety: Crossplane owns the Deployment. If Tilt patches the Deployment directly (replicas=1), Crossplane will reconcile it
   back.

  Solution: the dev overlay patches the AsyncActor CRD, not the Deployment:
  # asyncactor-dev-overlay.yaml
  spec:
    scaling:
      enabled: false     # disables KEDA ScaledObject
    workload:
      replicas: 1        # static 1 replica when scaling disabled
  Crossplane reconciles this into a Deployment with exactly 1 replica. No fight.

  Integration Architecture: Three Options

  Option 1: Asya provides CLI primitives, Tilt extension composes them

  Asya provides: asya config get, asya k dev overlay, asya flow compile, asya k apply.
  Tilt extension: A Starlark file in a git repo that calls these CLI commands and wires up k8s_custom_deploy + live_update.
  User writes: A Tiltfile that loads the extension.

  # ext://asya/Tiltfile (the extension — Starlark)

  def asya_dev(flow_name, sync_overrides={}):
      """Set up dev mode for all actors in a flow."""

      # 1. Read config from asya CLI
      cfg = decode_json(local(
          'asya config get build -o json',
          quiet=True,
      ))

      # 2. Discover actors in this flow from compiled manifests
      actors = decode_json(local(
          'asya flow actors %s -o json' % flow_name,
          quiet=True,
      ))

      # 3. Generate dev/ overlay (replicas:1, KEDA off, DEV_RELOAD=true)
      local('asya k dev overlay %s' % flow_name)

      # 4. For each actor, set up live_update
      for actor in actors:
          name = actor['name']
          image = actor['image']
          handler_path = actor['handler_path']   # e.g., ./src/handler.py
          container_path = actor['container_path']  # e.g., /app/handler.py
          role = actor['role']  # 'handler' or 'router'

          if role == 'router':
              # Routers are ConfigMap-based, no live_update needed
              # They get updated via flow recompilation
              continue

          # User can override sync paths per actor
          sync_paths = sync_overrides.get(name, {
              handler_path: container_path,
          })

          steps = []
          for local_path, remote_path in sync_paths.items():
              steps.append(sync(local_path, remote_path))

          # Optional: pip install on requirements.txt change
          if actor.get('requirements'):
              steps.append(sync(
                  actor['requirements'],
                  '/app/requirements.txt',
              ))
              steps.append(run(
                  'pip install -r /app/requirements.txt',
                  trigger=[actor['requirements']],
              ))

          k8s_custom_deploy(
              name,
              apply_cmd='asya k apply %s --overlay dev' % flow_name,
              delete_cmd='asya k delete %s --overlay dev' % flow_name,
              container_selector='asya-runtime',
              live_update=steps,
          )

          k8s_resource(name, labels=['actors'])

      # 5. Auto-recompile flow on source change
      flow_file = actors[0].get('flow_file')
      if flow_file:
          local_resource(
              'compile-%s' % flow_name,
              cmd='asya flow compile %s' % flow_file,
              deps=[flow_file],
              labels=['flows'],
          )


  def asya_dev_teardown(flow_name):
      """Clean up dev overlay on tilt down."""
      local('asya k dev overlay --remove %s' % flow_name)
